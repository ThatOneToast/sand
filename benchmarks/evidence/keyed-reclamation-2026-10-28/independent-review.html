Findings

TEST-01 · Low — Zero-length malformed containers are not exercised

scripts/validate_keyed_literals.py:594–603 tests malformed components.status only as integer 7. That value has a nonzero data-get result, so a broken implementation that drops compound-type predicates and relies only on a zero child-count result could still pass this native case.

Concrete missed regression: replace the container with [] or an empty string; deleting it because its result is zero violates the documented retention contract. The shared components container is also not tested with such values. The unit test at sand-core/src/entity/state.rs:4230 only requires one component compound predicate somewhere in the emitted body; it does not establish that both count and deletion lines for both levels remain type-guarded.

Add native retention cases for zero-length malformed values at both structural levels. Also exercise a UUID-only owner with a mismatching or missing UUID to validate the owner predicate behavior directly. The implementation at sand-core/src/entity/state.rs:2773–2788 currently has the appropriate guards; this finding is a coverage gap, not observed data loss.

TEST-02 · Low — Shared ownership does not assert callback suppression

scripts/validate_keyed_literals.py:614–620 asserts that the first archetype detach retains Status data and the final detach reclaims the owner. It does not count or trace cleanup-hook execution for these two operations.

Concrete missed regression: if the shared-claim guard were omitted only for the cleanup hook, while field deletion and presence reset stayed guarded, the first detach could emit SAND_STATUS_CLEANUP and execute arbitrary hook side effects prematurely. Both current storage assertions would still pass, and the final detach could invoke the hook a second time.

Trace these two actual archetype detach calls and require zero hook executions on the first and one on the last. The current shared-claim wrapper at sand-core/src/entity/archetype.rs:2742–2755 covers every detach command, including the hook and new helper calls; no current guard defect was found.

Reviewed behavior

  • state_detach_commands retains hook-before-score/data-deletion order, prunes after declared fields, resets presence afterward, and retains player suppression. Completed repeated detach cannot rerun a hook while presence remains absent.
  • state_data_remove_commands groups UUID resolution with each keyed field deletion. keyed_data_prune_commands separately groups resolution and pruning. Composition deduplication cannot strip the shared resolver lines from inside these helpers.
  • Pruning uses compound predicates and zero children for the component and components containers. Whole-owner deletion requires a matching typed UUID and exactly one child. Unknown fields and other components block whole-owner deletion; the indexed root and layout marker are not removed.
  • The scratch count is cleared on completed pruning; no callback runs between count and removal. Missing executors clear the scratch UUID before macro invocation. Field-level KeyedData::remove is unchanged.
  • The existing migration readiness guard wraps the entire detach sequence. Shared archetype claims wrap each command before deduplication. No recurring reclamation scan, offline/unloaded cleanup, death callback, or purge policy is added.
  • Rustdoc, book, layout contract and reclamation notes describe ordered, nontransactional cleanup. Hook replay before presence reset after interruption is explicitly documented; exactly-once interrupted cleanup is not promised.
  • The frozen harness includes actual prior-score message matching and baseline cleanup measurements. Prior-data reads, nested-owner retention, other-component retention, repeated detach, missing executor, field-only removal and cycles all have targeted assertions, subject to the gaps above.
