Reviewed guarantees

Direct keys and runtime ownership

sand-core/src/entity/state.rs stores owners under a quoted full signed-int-array UUID key. There is no numeric-ID allocator or cached scoreboard identity to contradict persistent ownership. Each operation still resolves the current executor, and the macro executes after an unchanged UUID copy. Missing executors remove scratch UUID before the copy; a missing macro argument prevents stale-owner access. Macro instantiation captures the outer UUID before nested callbacks. Authored payloads remain staged outside macro source and are cleaned up. Public field removal stays field-only.

Native evidence and exported entrypoints cover signed boundaries, literal payloads, alternating owners, actual nested callback get results (5 then 32), absent-owner set behavior, missing executors, two players and three entities in one tick, reconnect and actual entity unload/return.

Migration write ordering and interruption

sand-core/src/entity/keyed_migration.rs persists a complete row snapshot, validates exactly four UUID integers plus compound components, and records intent before copying an absent destination. Existing destinations without intent conflict even if identical. Whole-record comparison precedes the completion receipt. On the next invocation, the completed row is revalidated before committing its durable next cursor and removing the journal. The cursor validation accepts a retry after the cursor write without skipping the next owner.

Legacy retirement writes a finishing marker before source removal and then replaces metadata with version 2. Restarting on either side of removal is covered. Duplicate UUIDs, conflicting/partial/wrong-type destinations, malformed rows, invalid cursor/next metadata and unknown versions stop while preserving evidence. Compiler-owned completion receipts are explicitly trusted; arbitrary external edits to committed rows or forged receipts are outside the supported recovery model. No destructive ambiguity is hidden by the documentation.

Availability, dormant retention and exports

All keyed macros require version 2. Full component attach/detach sequences, including hooks, defaults and presence publication, are guarded by all relevant storage readiness conditions. Automatic player initialization retries; explicit entity attachments need caller retry as documented. This is an upgrade availability barrier, not an atomic transaction around arbitrary gameplay. Migration runs without selecting owners, so dormant and offline rows are included.

state/registry.rs, compiler/export/pipeline.rs and the shared lifecycle assembly provision standalone public KeyedData handles as well as State-backed fields. Deferred lowering is drained before sealing storage requirements. Export-scoped registries, private-objective collision validation, helper resolution and deterministic deduplication remain in place. Portable revision-one State cannot declare keyed fields; its shared helper-resolution regression protects the supported frontend boundary without claiming a new portable schema.

Benchmark interpretation

The maintained workload fixes one live active owner and 1,000 operations per wall sample while seeding 10, 1,000 and 10,000 historical owners. It independently checks an active executor, reached UUID reads, a successful get and changed values. This avoids the retained rejected candidate’s empty-selector measurement. Seeding, first migration step, remaining migration, warm reads/writes and saved storage size are separate.

At all populations, candidate warm reads report one UUID read, six explicit command evaluations including the wrapper, one successful get and zero successful mutation commands. Migration uses 21/2,001/20,001 bounded invocations. The layout removes native list-filter access and adds persistent key bytes; it does not claim smaller storage or fewer command evaluations. The baseline read probe uses an equivalent extracted legacy getter, whereas candidate reads invoke its export; both writes use actual exports. This producer difference is disclosed.

Timing is a single run per population including console barriers, JIT and host noise, without normalized warmup. It is not MSPT, latency percentiles or a whole-server complexity proof. Migration bounds are rows/emitted commands, not arbitrarily large payload bytes. Its mutation counter excludes execute-store side effects and total migration mutations are explicitly unmeasured. Cleanup is not measured in this slice. These limitations are accurately stated.
